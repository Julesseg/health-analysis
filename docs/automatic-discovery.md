# Automatic discovery

Discovered for you uses readable on-device history. The Discovery variables list controls which supported series can enter a search. Disabling a variable removes it from that search. Saved analyses keep their original question. The first version calibrates discovery for numeric daily quantities and Health resting heart rate or sleep duration. Explore can run additional configurations, including count analyses, whose discovery tests need separate validation.

## Search family and bounds

- Use a maximum of four enabled daily quantities in their stored creation order. A person can disable an earlier quantity to include another one. Disclose when an enabled input is outside the limit.
- Use at most one series per enabled output metric. Resolve the preferred source or the sole eligible source in the last year. When several sources contribute and there is no preference, skip that metric and ask for a source if no metric remains. If a preferred source has no eligible history, do not substitute a different source. A caller can restrict the search to explicit sources. Each generated configuration pins the resolved source.
- Use the previous 365 civil output days including the cutoff day, with only Health records completed by the cutoff. Use the same complete preceding 1-, 7-, and 30-day windows as Explore, including the sleep onset cutoff. A window can use behavior days before the 365-day output period.
- For each output and window, test the focal slope for each single quantity, that slope accounting for each other quantity individually, and one interaction per unordered pair. For an interaction, test the difference between the two condition estimates. Either orientation tests the same product coefficient. Use creation order to choose the displayed orientation. The condition estimates and fitted main effects provide context, so they add no hypotheses to the search.
- With four inputs, this is at most `2 × 3 × (4 + 12 + 6) = 132` configurations and at most six fits per configuration. Each full fit uses up to 365 output days and three fitted columns plus an intercept. The search reuses the same window summaries across questions and runs the fits off the main actor. Output normalization depends on the size of the locally imported history. Return at most five findings, ranked by the raw block test p-value, breaking ties by fixed enumeration order.

## Evidence

The ordinary Explore fit supplies the displayed effect, dependence-adjusted interval, coverage, and model limitations. A separate screen checks the selected contrast across five consecutive 73-day blocks of the fixed output period. In each block omit the first seven civil days and require the output anchor and every complete behavior day to lie within the remaining block. Use only rows with fully recorded inputs. This keeps days used for behavior windows from crossing block boundaries and leaves a gap between the dates used by neighboring blocks. The block fits use the same linear mean model with the same adjustment columns, including the centered product for an interaction. Centering within a block leaves the product coefficient unchanged. Its sign and null match the displayed condition difference because the focal and moderator ranges are positive.

Each block needs at least 16 complete output rows and at least five rows per fitted parameter. A rank-deficient or highly collinear block, missing block, or unusable block uncertainty withholds search evidence. Estimate the scalar contrast once in each block and use a two-sided Student t test with four degrees of freedom across the five estimates. This follows the grouped-estimator approach for approximate inference when the group estimates are sufficiently independent, centered at the same parameter, and approximately Gaussian. Each block may have a different variance. [Ibragimov and Müller](https://www.princeton.edu/~umueller/tstat.pdf)

Apply Holm's step-down correction at a 5% family threshold to the complete enumerated family, including candidates whose model or block fit is unavailable as p = 1. A full model with an interval crossing zero or a sign inconsistent with the group test cannot surface as a finding. Holm allows dependence across candidate tests when the individual tests are valid. The group approximation, limited sample size, longer dependence or trends, missingness, assumed values, and repeated searches limit the interpretation. The threshold describes one search under its assumptions. The displayed fit interval remains a per-model interval. Discovery confidence is capped at low and support from subsequent data is unassessed. [Holm](https://www.ime.usp.br/~abe/lista/pdf4R8xPVzCnX.pdf)

## Validation

Synthetic tests run through `HealthAnalysisApplication`. The null trials search all 15 configurations from two inputs, one output and three windows. Each of 64 seeded trials per scenario uses 395 behavior days, with two output days omitted in each 17-day span. The first scenario uses independent histories. The second uses separate AR(1) inputs and residuals with coefficient 0.86. The predefined limits are at most eight families with any Holm rejection per scenario and at least 56 usable focal tests per window.

| Null scenario | Families with a Holm rejection | Usable focal tests for 1 / 7 / 30 days |
| --- | ---: | ---: |
| Independent | 5/64 | 64 / 64 / 64 |
| AR(1), 0.86 | 2/64 | 64 / 64 / 64 |

The planted rolling-window checks use AR(1) inputs and residuals and require both seven- and thirty-day scenarios to select the correct window with an effect within 0.20 bpm of the known 1.8 bpm per 100 mg. The confounding check requires a marginal association to pass and its adjusted null to fail the screen, with the associated covariate passing and an exactly collinear pair deemed unestimable. The planted interaction has to surface the condition difference within 0.25 bpm. A deterministic two-output AR(1) null fixture checks the full 132-member family with varying outputs. It requires at least 96 estimable contrasts and zero Holm rejections for that fixture. The targeted debug run estimated 122 contrasts and took 1.42 seconds for the first search on the development Mac. These finite simulation checks give evidence for the tested designs. They do not establish calibration for arbitrary autocorrelation, nonstationarity, or extensions to different models.

## Saved questions and refresh

- `HealthAnalysisApplication.discover(asOf:timeZone:enabledSeries:)` evaluates an immutable snapshot of reconciled local data. `refreshDiscoveries` publishes the newest valid request to the observable `discovery` activity. An unsuccessful read leaves an earlier successful report visible for the same selection scope.
- A discovery carries the exact tested configuration, pinned output source, model, selected contrast, method version, selection boundary, and original result and update time. Open it through the usual result and builder. Saving the unedited question persists that completion. Editing any part of the configuration detaches the prior result.
- `SavedAnalyses.discoveryBaseline(for:)` continues to return the original selected completion after a regular refresh of the same saved question. To evaluate genuinely subsequent data, start after its cutoff, using a window whose earliest behavior day and output anchor are after the boundary. Exclude corrections and deletions to historical rows from subsequent-data evidence. The original condition levels remain available in the interaction estimate for comparing the same contrast. The original selection and an ordinary refreshed fit do not establish persistence.

## Health-triggered refresh

- The iPhone app registers HealthKit observers for the imported sample types at launch and requests hourly background delivery. Delivery records a pending check before acknowledging HealthKit. The app processes pending work while active and checks again at foreground activation or when protected data becomes available. A notification during a read requests a follow-up from the resulting anchor. [Apple observer queries](https://developer.apple.com/documentation/healthkit/executing-observer-queries)
- The Health check drains anchored pages of up to 500 records per stream. The app commits reconciled records and anchors together only when the check completes. Automatic analysis and discovery run in the foreground against that committed local history. A failed or interrupted check keeps the previous checkpoint and successful results, including their timestamps, and makes retry available. The daily log uses its own store.
- `refreshReconciledHealthInsights` refreshes affected followed questions and the discovery selection shared by Insights. Unchanged, replayed deltas leave existing results in place. Preferred-source changes invalidate questions that use that preference. Explicitly pinned questions retain their source. The application checks the Health and daily-log revisions before publishing computed results and applies the saved question’s existing request and configuration guards.
- Physical-device HealthKit delivery, including add/delete wakeups and recovery from a genuinely protected store, remains unverified. Signing the development build requires an authenticated Xcode account and development profile. The native foreground fixture exercises the view flow without opening Apple Health. It can be run by the native CI suite.
