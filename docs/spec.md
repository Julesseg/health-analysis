# Personal health analysis app specification

## Problem Statement

I record health measurements and behaviors in different places and want to understand how they relate over time. Apple Health aggregates many of my measurements, including Garmin Forerunner 965 HRV transferred through Livity, but it does not answer my personal questions about combinations of behaviors, medications, activity, sleep, and recovery.

I want to choose a question myself or let the app surface patterns worth investigating. A useful answer must account for other tracked inputs, consider both recent and accumulated behavior, and explain how much evidence supports the result. Logging must be quick enough for daily use and support catching up afterward. The interface should feel like a standard native iPhone app.

## Solution

Build a personal native iPhone app that reads Apple Health, stores its own manual daily logs, and performs exploratory association analysis on the device. Start with Apple Health as the aggregation point and validate the existing Garmin-to-Livity-to-Apple-Health HRV pipeline before considering another integration.

Let the person choose any supported input or combination of inputs and any supported output, inspect adjusted associations and interactions, and compare complete preceding one-day, seven-day, and thirty-day behavior windows. Default to the full usable joint history, with an optional shorter analysis period. Offer editable presets and automatic discovery across enabled variables.

Present each result with a plain-language finding, an appropriate chart, effect size, uncertainty, and an explained confidence index. Keep associations distinct from causal effects. Preserve source identity, coverage, and the difference between explicit observations, assumed defaults, and missing imported measurements.

Use three native tabs: Insights, Explore, and Data. A separate Log action opens a daily form with a date control and prefilled values. Valid field changes save automatically; Confirm day separately reviews the whole form. Use standard SwiftUI controls and the system's native Liquid Glass appearance.

## User Stories

1. As a person exploring my health, I want to read my Apple Health measurements in one app, so that I can analyze the information already collected by my devices and services.
2. As a Garmin Forerunner 965 wearer, I want to use the HRV that Livity transfers to Apple Health, so that I can keep my existing recording workflow when its records are suitable.
3. As a person using this app for myself, I want my manual logs and analysis to remain on my iPhone, so that I can use the app without operating a server.
4. As a person granting access to health data, I want Apple Health access to be read-only, so that the app can analyze my records without changing them.
5. As a new user, I want a short explanation before the Health access request, so that I understand what the app needs the measurements for.
6. As a new user, I want to see which measurements and dates are readable, so that I know what questions I can investigate immediately.
7. As a new user, I want to skip manual tracking setup, so that I can first explore existing measurement history.
8. As a person tracking my behavior, I want suggested variables and editable defaults, so that I can begin without designing every field myself.
9. As a person checking imported data, I want to inspect measurement history and coverage, so that I can see gaps and source changes before interpreting a finding.
10. As a person with multiple data sources, I want to see and change the preferred source for a metric, so that an analysis uses the series I intend.
11. As a person using bridged measurements, I want metric meaning and source identity to be preserved, so that incompatible HRV measures are not silently combined.
12. As a person with overlapping imports, I want duplicate records counted only once, so that repeated imports do not exaggerate the amount of evidence.
13. As a person whose source records change, I want corrections and deletions reflected in subsequent analysis, so that saved findings use the available current data.
14. As a person with unreadable or absent measurements, I want neutral availability wording and access to source information, so that the app does not claim to know why records are unavailable.
15. As a person refreshing while the phone is locked, I want previous readable results preserved after an access failure, so that a failed read does not appear to erase my history.
16. As a person logging daily values, I want one form containing all my manually tracked variables for the selected day, so that I can review and update them together.
17. As a person opening a daily log, I want saved entries or configured defaults already displayed, so that I only need to change values that differ.
18. As a person catching up on logging, I want a date control for backdating, so that I can enter values for their actual day.
19. As a person revisiting a day, I want its previously saved values displayed, so that my earlier entries remain available.
20. As a person tracking quantities, I want values with units and appropriate entry controls, so that entries have a clear and consistent meaning.
21. As a person tracking behaviors, I want count and yes/no variables, so that I can record occurrences and presence without forcing them into an unsuitable scale.
22. As a person tracking subjective observations, I want ratings and categories, so that I can record stress, energy, or another observation in a suitable form.
23. As a person interested in daily timing, I want optional time-of-day fields such as last caffeine time, so that I can investigate timing as well as amount.
24. As a person backdating a timed entry, I want exact and approximate times distinguished, so that the analysis can expose the precision of my recollection.
25. As a person configuring tracking, I want a default value for each manual variable from a chosen start date, so that an unlogged day has the assumption I intended.
26. As a person adding a new variable, I want applying defaults to older history to require an explicit choice, so that setup does not silently invent a longer history.
27. As a person inspecting my data, I want assumed defaults distinguishable from explicit observations, so that I can assess how much of an analysis depends on assumptions.

29. As a person editing a daily value, I want valid changes to save automatically, so that I do not need to save the whole day to retain an entry.
30. As a person analyzing a recent edit, I want individually saved entries available before day review, so that Confirm day is not a prerequisite for using recorded data.
31. As a person reviewing a day, I want Confirm day to validate every displayed value including unchanged defaults, so that the app records that I checked the whole form.
32. As a person using autosave, I want saving feedback separate from day review status, so that I can tell whether my entries are persisted and whether I reviewed the day.
33. As a person leaving a daily form, I want valid edits retained for their original date without a save/discard prompt, so that navigation does not create an extra logging step.
34. As a person entering an incomplete or invalid value, I want inline validation without replacing the last stored valid value, so that temporary typing does not corrupt my log.
35. As a person experiencing a persistence error, I want my entered value retained with accurate retry feedback, so that I can recover without re-entering it or assuming it was saved.
36. As a person with missing sensor records, I want those records to remain missing rather than receive manual defaults, so that assumed behavior does not manufacture measurements.
37. As a person asking a health question, I want any supported tracking variable selectable as an input or an output, so that its role follows my question rather than a fixed category.
38. As a person with several related behaviors, I want more than two inputs in an analysis, so that I can investigate their associations together.
39. As a person examining a combination of behaviors, I want interaction analysis, so that I can see whether one input's association varies with another.
40. As a person concerned about other influences, I want suggested adjustment inputs that I can inspect and change, so that I can account for other recorded variables.
41. As a person reading an adjusted result, I want the actual modeled inputs shown, so that I understand what the analysis accounted for.
42. As a person whose behaviors occur together, I want the app to explain when their individual associations cannot be distinguished, so that it does not present unsupported separate contributions.

44. As a person investigating accumulated behavior, I want complete preceding seven-day and thirty-day windows, so that I can explore longer-term associations.

60. As a person who does not know what to ask, I want automatic discovery across enabled variables and behavior windows, so that the app can surface candidate patterns.
61. As a person managing discovery, I want the search limited to enabled variables and feasible comparisons, so that findings are relevant and computation remains practical on my phone.
62. As a person reading a discovery, I want it identified as exploratory and assessed in the context of the search, so that a selected pattern is not presented as though it were the only comparison.
63. As a person following a discovery, I want subsequent data used to assess its persistence, so that the initial pattern can gain or lose support over time.
64. As a person checking the app, I want discovery findings presented inside it, so that reviewing them fits the initial application workflow.
65. As a person reading a result, I want a plain-language finding, chart, effect size, and confidence index near the top, so that I can assess its meaning without opening technical details first.
66. As a person reading an analysis, I want an insufficient, low, moderate, or high confidence grade with reasons, so that I can judge the quality of its evidence.
67. As a person comparing findings, I want effect magnitude separate from evidence quality and uncertainty, so that a large estimated association is not mistaken for a well-supported one.
68. As a person interpreting a finding, I want association wording without implied causation, so that the app reflects what this analysis can establish.
69. As a person inspecting evidence, I want coverage, variation, defaults, missingness, approximate entries, sources, and adjustment inputs available, so that I can understand what shaped the result.
70. As a person comparing overlapping behavior windows, I want uncertainty and confidence to account for dependent observations, so that repeated information is not treated as independent evidence.
71. As a person receiving an insufficient-evidence result, I want the specific limitation and a route to inspect the data, so that I understand why the question cannot yet be answered.
72. As a person reading a near-zero estimate, I want it distinguished from an unavailable or highly uncertain estimate, so that absence of a usable answer is not presented as evidence of no association.
73. As a person inspecting individual contributions, I want estimated differences with uncertainty ranges, so that the chart communicates both direction and precision.
74. As a person inspecting an interaction, I want labeled comparisons between conditions, so that I can understand how the combination relates to the output.
75. As a person inspecting underlying measurements, I want timelines or scatterplots clearly distinguished from adjusted estimates, so that observed data and modeled results are not confused.
76. As a person refreshing an existing analysis, I want the last successful result retained with its update time and refresh status, so that I can keep reading while new data is processed.
77. As a person encountering a refresh failure, I want the previous result preserved with freshness and retry information, so that I can distinguish an older result from a current successful calculation.
78. As a person starting a new analysis configuration, I want a loading state without an unrelated previous result, so that the visible answer always matches the question.
79. As an iPhone user, I want standard native navigation, forms, controls, and Liquid Glass presentation, so that the app feels familiar and readable.
80. As a person moving through the app, I want Insights, Explore, and Data tabs with a separate Log action and accessible Settings, so that analysis and daily entry are easy to reach.

## Implementation Decisions

- **Architecture and ownership:** Build a native iPhone app with on-device storage and computation for personal use. Apple Health is read-only. App-owned manual logs, settings, saved analysis configurations, and review metadata remain local. No application backend is required for this version.
- **Existing state:** The repository contains accepted design documentation and a domain glossary. There is no native application, persistence implementation, analysis engine, or existing test suite to extend. Framework choices beyond the agreed native interface and HealthKit integration are not settled by this specification.
- **Module boundaries:** Use clear responsibilities for Health data ingestion and provenance; tracking definitions and daily logs; temporal dataset preparation; association estimation and evidence assessment; saved analyses and discovery; and native presentation. These responsibilities describe contracts, not a required number of types or packages. Keep coordination available through a small application-facing boundary so observable workflows can be tested together.
- **Ingestion contract:** Obtain readable records and relevant changes through HealthKit, preserving source identity, metric identity, units, record timing, and record identity sufficient for repeatable import, deduplication, and correction handling. Never turn unreadable or missing measurements into zeroes or manual defaults. Make the preferred source per metric visible and editable.
- **HRV provenance gate:** Treat the user's Forerunner 965 and Livity bridge as the initial candidate pipeline. Before relying on it, inspect the actual exported metric, units, aggregation, timing, historical coverage, duplicates, corrections, and source metadata. Do not assume a bridge changes one HRV measure into another or that all HRV sources can be pooled. Direct Garmin integration is deferred unless an actual coverage need justifies revisiting scope.
- **Availability contract:** Empty HealthKit results do not establish whether read access was denied or measurements do not exist. Present neutral readable-coverage information. A protected-data or refresh failure preserves previously successful data and results with accurate freshness. Do not assume continuous background access.
- **Tracking definitions:** Support named quantities with units, counts, yes/no values, ratings, and categories, with optional daily time-of-day fields. A supported tracking variable can be an input or an output when the requested analysis has a meaningful definition and sufficient data. This is not a promise to ingest every HealthKit type or fit every possible combination without validation.
- **Manual defaults:** Associate configured defaults with their effective history so the app can distinguish assumed values from observations. Apply defaults from the chosen start date; filling older history requires an explicit choice. Preserve enough provenance for analysis to report its use of defaults. An explicit zero is a recorded value, not missing data.
- **Daily persistence and review:** A daily log is keyed to its selected date and contains the applicable tracked fields. Opening the form shows saved values where available and configured defaults otherwise. Valid individual edits persist automatically and become available to analysis without confirming the day. Untouched values remain assumed defaults until reviewed. Confirm day confirms all displayed values, including unchanged defaults, and records whole-day review separately from field persistence. Preserve the origin of confirmed defaults so review does not erase how a value was obtained.
- **Entry and failure behavior:** Date changes and dismissal retain valid edits for their original date without a save/discard prompt. There is no Unknown option or per-day Unknown override in the manual form. Invalid or incomplete text receives inline validation and does not overwrite a stored valid value. A persistence failure retains entered values and presents accurate saving and retry feedback. Backdated entries retain the distinction between exact and approximate times.
- **Manual clock readings:** Adding a time-of-day variable is optional. Once its default becomes effective, each applicable day displays a concrete local hour and minute. Defaults and reviewed assumptions carry no observation precision. Clock edits save as exact unless marked approximate, and changing that mark is itself a saved edit. The daily log stores the chosen Gregorian tracking day and wall-clock reading independently of any UTC instant or time zone. A new log opens on today in the device’s local time zone. Changing the device time zone or passing midnight leaves an open log on its selected day. Reopening a historical day after travel shows the same saved hour and minute. Skipped and repeated hours on daylight-saving transition days are accepted as wall-clock readings. Exact describes the recalled minute, with no offset or DST occurrence implied. Any future analysis that needs a chronological instant must define a separate interpretation.
- **Analyzing clock times:** See [clock-time associations](clock-associations.md) for supported roles, the fitted clock interval, recorded precision, and sleep timing provenance.
- **Analysis configuration:** Represent the selected output, one or more inputs, adjustment inputs, interaction choices supported by the analysis, behavior window, and historical analysis period. Suggest adjustment inputs and expose which are used. Do not reduce multi-input analysis to independent pairwise correlations. Individual contributions and interactions both belong to the requirement.
- **Temporal dataset contract:** Construct complete preceding one-day, seven-day, or thirty-day behavior windows anchored to each output. Include intervening behavior and exclude behavior after the relevant output. Label overnight sleep by its wake date. Keep the behavior window distinct from the historical analysis period. Default to the full usable joint history after required lookback, and expose actual usable dates, gaps, and overlap. Allow a shorter analysis period.
- **Temporal details requiring validation:** Specify exact output anchors, day boundaries, aggregation rules, partial-window eligibility, time zones, travel, daylight-saving changes, and approximate-time handling before relying on calculated results. These are necessary implementation decisions to validate, not algorithms already chosen during the interview.
- **Estimation contract:** Estimate supported adjusted associations and interactions with effect sizes and uncertainty. Report insufficient data, inadequate variation, or inputs that cannot be distinguished. Distinguish an unavailable estimate from an uncertain estimate and from a precise estimate near zero. Label results as associations rather than causal effects.
- **Evidence contract:** Every analysis exposes an insufficient, low, moderate, or high confidence index with inspectable reasons. Keep the grade separate from effect size, practical importance, and uncertainty. Explain usable history, overlap, variation, source changes, explicit observations, defaults, missingness, approximate entries, adjustment inputs, temporal dependence, stability, search scope, and support from subsequent data as applicable. A grade is not a probability that an association is true or causal.
- **Statistical validation gate:** Select and validate estimation methods for the supported variable types, uncertainty methods suitable for dependent observations and overlapping windows, treatment of automatic search selection, insufficient-evidence rules, and confidence-grade criteria. No formula, numeric confidence weights, sample-count threshold, or grade calibration has been agreed. Do not invent those as product requirements or claim that an unvalidated score fulfills this contract.
- **Presets and discovery:** Offer editable starting analyses using HRV, sleep duration and timing, and resting heart rate, with available and enabled inputs such as activity/running, caffeine, alcohol, medication intake, stress, and energy. Search enabled variables across the agreed windows, including adjusted analyses. Bound search breadth and refresh work to practical on-device execution. Expose exploratory status, account for the search when assessing evidence, and evaluate persistence using subsequent data. Initial findings appear inside the app.
- **Saved analysis contract:** Save the question configuration so it can refresh with new data and be pinned to Insights. Preserve question identity across refreshes. Returning from a result preserves the editable configuration. Keep pinned analyses in stable positions.
- **Refresh result contract:** Preserve the last successful result for the same configuration while refreshing; expose the successful update time, current work, failure, and retry state accurately. A new configuration without a successful result uses a loading state and must not display another configuration's result. Late or failed work must not replace the visible answer with a result for a different question.
- **Navigation and hierarchy:** Use Insights, Explore, and Data as the three bottom tabs, each with native navigation. A separate Log action opens the daily form; a gear action opens Settings. Insights orders Following, Discovered for you, then Latest measurements. Explore shows editable Output, Inputs, Account for, Behavior window, and History rows on one screen.
- **Result presentation:** Lead with the finding, chart, effect size, confidence grade, and limitations that materially affect interpretation. Offer deeper inspection of sources, usable history, adjustments, defaults, and uncertainty. Show estimated individual differences with uncertainty ranges, interactions as labeled comparisons between conditions, and observed timelines or scatterplots separately from adjusted estimates.
- **Native visual implementation:** Use standard SwiftUI navigation, lists, grouped forms, fields, steppers, toggles, pickers, date pickers, toolbars, buttons, sheets, and dialogs, with Swift Charts for analysis visualizations. Let system navigation and controls provide the native Liquid Glass appearance; keep content surfaces readable. Use system typography, layout metrics, semantic colors, SF Symbols, and one restrained tint. Earlier HTML sketches communicate hierarchy only, not native appearance or authoritative control styling.
- **Accessibility and localization:** Support system light/dark appearance, Dynamic Type, VoiceOver, contrast settings, Reduce Transparency, and Reduce Motion. Confidence and direction require text labels. Present dates, times, and units according to locale and settings.
- **First use:** Explain and request Health access, show readable metrics and coverage, and offer manual variables and editable defaults. Permit skipping manual setup and exploring existing history immediately. Do not silently apply new defaults to earlier history.

## Testing Decisions

- **Existing prior art:** There is no app or test harness in the repository. Earlier HTML examples use fictional data and verify neither native controls nor statistical correctness. Documentation checks are not application acceptance tests.
- **Confirmed primary seam:** Use one application-facing acceptance boundary above ingestion, local persistence, temporal dataset preparation, estimation, evidence assessment, saved analyses, and discovery. Drive user operations and inspect externally visible data, results, and states through that boundary. Substitute a deterministic Health data source at the platform edge and use a temporary local store that can be reopened. The user confirmed this boundary, with separate native UI and real-device HealthKit checks, on 2026-11-17.
- **What makes a good test:** Demonstrate observable behavior and meaningful failure handling with realistic histories and known expectations. Do not assert private helper calls, internal type structure, incidental query order, or screen implementation details. Use the fewest seams that can establish the contracts. Add a lower-level numerical test only where the acceptance boundary cannot meaningfully establish a statistical property.
- **Imported history:** Exercise repeated imports, overlapping sources, preferred-source changes, incompatible metric identities, source corrections and deletions, gaps, empty readable history, and failed reads. Verify that duplicates do not increase evidence, incompatible series do not merge silently, and unavailable records do not become defaulted measurements.
- **Daily log durability:** Edit values, change dates, dismiss, reopen the store, and revisit days. Verify autosave without Confirm day, whole-day review including untouched defaults, preserved default provenance, chosen default start dates, explicit opt-in to older defaults, approximate times, inline validation, and recovery from a failed persistence attempt. Keep saving status distinct from review status.
- **Temporal correctness:** Use small histories with hand-checkable eligibility and aggregation. Verify output anchoring, wake-date labeling, exclusion of later behavior, complete one/seven/thirty-day windows, first jointly analyzable history, shorter periods, coverage gaps, and validated handling of time-zone and day-boundary cases.
- **Analysis correctness and evidence:** Use deterministic synthetic histories with known associations, confounding, interactions, collinear inputs, little variation, missingness, and default-heavy observations. Use appropriate simulation-based validation for uncertainty under dependent data, automatic search selection, null associations, and confidence criteria once methods are specified. Predefine tolerances and expected properties rather than freezing one arbitrary numerical implementation. A strong test distinguishes failure to estimate from an estimate near zero and verifies evidence explanations as well as numbers.
- **Saved questions and discovery:** Verify enabled-variable scope, bounded candidate search, honest exploratory labeling, saved configuration refresh, new-data persistence checks, pinning, stable Following positions, preserved editor configuration, and results that remain attached to the question that produced them.
- **Refresh and failure states:** Verify prior successful results remain visible during a refresh and after failure with correct freshness, while a new question cannot inherit an unrelated result. Exercise empty data separately from failed access and persistence failures separately from unsaved invalid text.
- **Platform validation outside the primary seam:** A small set of HealthKit integration checks on a suitable device must establish actual readable record semantics and access behavior, including the user's Livity HRV pipeline. Native UI checks must exercise the daily form, analysis builder, result and refresh states, navigation, light/dark appearance, large text, VoiceOver, contrast, and reduced transparency/motion. These checks complement deterministic acceptance tests; no simulator fixture proves the contents of the user's Apple Health store.
- **Verification boundary:** This specification establishes intended behavior and the agreed test approach. No native build, real-device data inspection, statistical engine validation, or native visual verification has been completed.

## Out of Scope

- Apple Health writes or synchronizing app-owned logs back into Apple Health.
- A web frontend, custom backend, cross-device app synchronization, or remote processing of health data in the initial version.
- Direct Garmin integration unless later data validation establishes a concrete need and scope is revisited.
- Export, restore, and CSV export for now.
- Medical diagnosis, treatment recommendations, or causal conclusions from observed associations.
- Separate delay or lag controls that omit intervening behavior from the agreed complete windows.
- Per-event logging as the primary entry flow or an Unknown choice in the daily manual form.
- Out-of-app discovery notifications in this version.
- Support for every HealthKit record type or arbitrary statistical comparisons without a meaningful supported definition.
- A custom component library, simulated glass styling, or treating illustrative HTML as native UI verification.
- An already selected database, test framework, minimum OS version, complete statistical method, confidence formula, or implementation task breakdown. Those choices are not established by the interview.

## Further Notes

This specification consolidates the product and interface decisions from the grilling session through 2026-11-17. The latest clarification takes precedence over earlier sketches: individual daily values autosave, Confirm day reviews the whole form, and changing dates does not prompt to save or discard. The visual direction is native iOS Liquid Glass with vanilla components.

Before implementing dependent features, validate the actual imported HRV records, define temporal boundaries and import identity handling, and specify and validate the statistical procedure and confidence criteria. These are engineering validation tasks rather than requests to reopen settled product decisions.
